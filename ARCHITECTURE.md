# Vinput architecture

For engineers and coding agents. What the app does for its user is in [README.md](README.md); the local API is in [docs/api.md](docs/api.md); cutting a release is in [docs/release.md](docs/release.md).

## Crates

One Cargo workspace. The version of every crate is `[workspace.package] version` in the root `Cargo.toml`; lints and the release profile are set there too.

| Crate | What it is | May depend on |
| --- | --- | --- |
| `crates/putlab-core` | What Vinput shares with the programs beside it: plain HTTPS requests, checked downloads, the update check, the account, the credential store, the look at this PC's hardware, the names of a running copy, the selected text of the program in front, and the model engine with the way a model that writes is asked. No window code, and nothing that listens, speaks or types. | third-party crates |
| `crates/vinput-core` | The engine: microphone, speech providers, typing, voice memos, settings, models, the local API. No window code. What moved to `putlab-core` still goes by its old name here (`vinput_core::download`, `cloud`, `update` and so on). | `putlab-core`, third-party crates |
| `crates/vinput-view` | The contract between the engine side and the windows: `View` (everything a window shows), `Event` (host to window), `Command` (window to host). Data only, `serde`. | `serde`, `serde_json` |
| `crates/vinput-host` | The resident Windows process: message loop, hotkeys, tray icon and menu, listening indicator, install and uninstall, and the host's end of the line to a window process. | `vinput-core`, `vinput-view`, `vinput-ui` (its dialogs only) |
| `crates/vinput-stand-in` | A test crate: a stand-in for a window process, and the tests that run the line between host and window over real pipes with it. Not part of a release. | `vinput-ui`, `vinput-view`, `vinput-host` (tests) |
| `crates/vinput-ui` | The windows (Settings and its pages, the update window). Draws a `View`, reports `Command`s. Knows nothing about the engine. | `vinput-view` only |
| `crates/vinput` | The binary. `main.rs` parses the command line and calls the crates above; `build.rs` embeds the icons and marks the Windows libraries that load on first use. | all of the above |
| `apps/hub` | The PUTLAB hub (`putlab.exe`): one window that installs, updates and opens the programs of the family and shows the account they share. Its own version. | `putlab-core`, `vinput-view`, `vinput-ui` |
| `apps/voutput` | Voutput (`voutput.exe`): reads the selected text aloud, or a summary of it. Its own version. | `putlab-core`, `vinput-view`, `vinput-ui` |
| `bridges` | A separate private program (`vinput-bridges`) that uses only the local API. Its own version; not part of a release. | `vinput-core` (for `api::Client`) |

Three rules keep the split honest: `vinput-ui` never depends on `vinput-core` or `vinput-host`; `vinput-core` never depends on a window or on `vinput-view`; and `putlab-core` depends on none of the others, and the programs under `apps/` never depend on `vinput-core` or `vinput-host`, so nothing of dictation is in their executables.

## Processes

```text
vinput.exe --background            resident, one per user
  main thread        message loop: hotkeys, tray, timers, indicator
  vinput-api         the local API on \\.\pipe\vinput (single-threaded async runtime)
  vinput-stt         network thread of an online speech provider, if one is chosen
  vinput-pro         one per request about the VinPUT Pro account, short-lived
  vinput-google      one per question the setup of a Google service asks, short-lived
  vinput-microphone  keeps the last session's microphone stream, stopped, for two minutes; asleep otherwise
  vinput-sound       plays the sounds of a start and a stop; keeps its stream to the speakers for two minutes; asleep otherwise
  vinput-dictation   one per running session: microphone -> provider -> typing
  vinput-action      one per run of an action of the user's own: its program, then typing or copying what it wrote
  vinput-recognizer  one per session, short-lived: asks the provider for its session
  vinput-caret       only while the indicator follows the caret: asks the foreground program where it is
  vinput-local-stt   one per running session with a local model: posts its stretches to the engine
  whisper-server     child process, only with a local model; suspended while idle

vinput.exe ui <window>             exists only while a window is open
  stdin   <- Event,   one JSON object per line   (state to show, page to turn to, close)
  stdout  -> Command, one JSON object per line   (what the user did)
```

- The resident process owns all state. A window process keeps none beyond what is being typed: every `Event::State` carries a complete `View` and replaces the one before.
- Because standard output is the line, nothing in a window process may print to it. Diagnostics go to standard error or the log.
- A session is `AudioSource -> Transcriber -> TextSink` (`vinput-core/src/pipeline.rs`); each stage is a trait with a fake for tests.
- Nothing is polled for while idle, and no thread is waited for on the main thread. Every other thread leaves what it has found where the host looks for it and posts a message to the hidden window (the numbers are in `vinput-host/src/windows.rs`). That goes for a session too: the last thing its thread does is put its text, memo or error in place and post `SESSION_ENDED`, so a result is passed on when it exists, not at the next look. The only timers of the main thread are the 33 ms tick while a session is listening (key release, indicator), the one of the indicator while it glows or fades after that, the 250 ms one while a window is open, and the update check every six hours. Four other threads sleep until a time of their own, each only for a while after a dictation and none by polling: `vinput-microphone` until the stream kept ready is closed, two minutes after the session that left it; `vinput-sound` until its stream to the speakers is, two minutes after the last sound; with Gemini, the network thread until the session prepared ahead is let go after 90 seconds, and with VinPUT Pro until the connection kept ready is; with a local model, `vinput-local-idle` until the engine is suspended, half a minute after its last use, and then until it is ended, ten minutes after its last dictation. Once those have passed nothing in the process is waiting for a time at all.
- The main thread never waits for the program that is dictated into. Where its caret is, only that program can say (accessibility), so `caret::Watch` asks it on `vinput-caret`, which is started when the indicator appears at the caret and let go of, not joined, when listening ends. The indicator draws from the last answer. A program that hangs keeps that one thread until it answers or is closed, and at most four such threads exist at once; hotkeys, and with them stopping, are never held up.
- Escape calls a dictation off. It is a hotkey registered with Windows like the others, so there is still no keyboard hook, but it is registered only while a session listens or a stopped one is still at work and was not called off (`Controller::can_cancel`), and unregistered the moment that is no longer so; a registered hotkey is taken from every other program, and Escape belongs to all of them. Calling off sets a flag the session's thread reads: its sink lets text fall from then on, no Enter, search or memo follows, and a failure is not reported. The thread itself still ends when the recognizer has answered, and says so as always; a `capture` session ends with an empty text for the program that waits for it.
- Enter ends a dictation that types at the caret (F1, F2), and is a hotkey too, registered only while such a dictation listens or the one Enter ended is at its last words (`hotkeys::hold_finish`). It has to be taken from the focused program: left alone it would arrive before the last words. `Host::enter` tells the session (`Controller::enter`) and stops it; the session presses Enter after its last words, once, whichever key started it, and not at all if it fails or is called off. A hotkey also catches the Enter a session types itself, so every Enter typed is announced to the host thread with a sent message (`TYPING_ENTER`, answered in the window procedure), which unregisters the key around it (`hotkeys::typing_enter`). Search, memo and `capture` sessions leave Enter alone.
- A quiet setup (`--install --quiet`, `--uninstall --quiet`) is what a package manager runs and waits for. It never shows a window, a failure included; the exit code and the log say how it went. It does not start Vinput on a new install, because the tray program would keep the caller waiting for as long as the user is signed in; it makes the Start menu entry and the startup entry itself (`host::register_installed`). A Vinput it had to stop is started again, and everything setup starts is cut loose from it (`install::spawn_detached`: no handles, a process group of its own, out of the job where Windows allows). A start with `--background` reports a failure the same way, to the log and not in a window.
- The speech provider is set up once at start, in the background (`stt::connect_in_background`), so that a key press has as little left to do as possible. This is deliberate; do not make it lazy. What is kept ready differs by provider:
  - Google Cloud keeps its gRPC connection and an access token for as long as it runs, so a press only opens a stream on it.
  - Gemini has nothing that sessions can share but the TLS settings: every session is a WebSocket of its own. So one whole session is connected and set up ahead, when the provider starts and when the audio of a dictation ends, and the next press takes it over. It is let go after 90 seconds without a press; from then on nothing is connected and no timer runs, and a press connects for itself. The reasons for the numbers, and what happens when a prepared session has died, are at the top of `vinput-core/src/stt/gemini.rs`.
  - A local model with a server keeps the engine process running with the model loaded, and lets it go after a while without use.
  - VinPUT Pro keeps an access token in memory, fetched when the provider starts and traded for a new one after a dictation when it would run out within twenty minutes; every dictation is a WebSocket of its own, opened at the press with that token. After an hour without a dictation the next press fetches a token first, and connects while it does. When a dictation ends, one connection to the server is made and kept for 90 seconds, with TLS set up and nothing asked on it yet, so the next press only asks for the WebSocket; after that it is closed, nothing is connected and no timer runs. See the top of `vinput-core/src/stt/cloud.rs`. What Gemini and Pro share (the network thread, TLS, connecting in two steps, the dictation's end of a stream) is `stt/live.rs`.
  - When the month's hours of VinPUT Pro are used up, a model on this PC serves in its place (`vinput-core/src/stt/standby.rs`). `settings.provider` stays VinPUT Pro: that the hours are used up is a state of the running process, one number in memory (until when), set when the server refuses a dictation with `quota_exceeded` or the account says none are left, and gone when that time has passed or the account says there are hours again. After a restart it is found out again: the host asks the account once at start if VinPUT Pro is the chosen model, and a refusal sets it in any case. Which provider serves a key press is that number read: while it is zero nothing else is looked at, not even the clock, and while it is set no stream is asked for, so a press costs no round trip that would only be refused. A dictation the server refuses, at its start or in the middle, is handed to a session of the local model together with the audio the server did not count (`Leftover` in `stt/cloud.rs`), and goes on. The model is `last_local_model` of the settings (what was in use when an online model was chosen) if it is still installed, else the first installed one in the order of the catalog, but never one that knows none of the configured languages, and one that knows all of them before one that knows some (`models::spare`, `Model::languages`); nothing is downloaded. It is set up lazily and loaded ahead on `vinput-connect` when less than five minutes of the month are left, counted down from what each stream reports as counted, or when the hours have run out; from then on it is suspended and let go like any local model. No timer is added: the time until which it serves is compared when a key is pressed or a window is drawn. What the windows show of it is the account's own numbers plus the name of that model (`Pro::spare` in `vinput-view`); the host says it once in a notification (`pro_after_session`).
  - The same model serves when the server of VinPUT Pro is out of reach: a stream that cannot be opened in time, one that is open and says nothing (it is pinged once a second, and a server that is alive answers whether or not anybody speaks), a connection that breaks, a server that says it is failing. Whatever may have passed by the next press counts (`cause_of` in `stt/cloud.rs`); what only the account can put right still ends the dictation and says so. The dictation is handed over as above, with the audio the server did not turn into settled text: the server says with each settled text how far into the audio it reaches (`until`), so the model begins at the end of the last typed word, the server's guess is withdrawn, and nothing is lost or typed twice. The session that takes over in the middle of a dictation is started on a thread of its own (`stt/deferred.rs`), so the thread that reads the microphone never waits for a model to load, and the model is loaded ahead when a connection takes longer than a healthy one. Nothing lasting is concluded: the server is left alone for 15 seconds after the first such dictation, twice as long after each further one in a row, two minutes at most; a press in that time is served by the model at once, the first press after it tries the server again, and one dictation the server serves forgets it all (`Standby::stand_in`, `cover`, `reached`). All of it is read from memory at a key press; no timer, no probe while idle. The waits, and the measurements they come from, are at the top of `stt/cloud.rs`. The host says it once, without a sound, each time the server goes out of reach (`pro_stood_in`), and the tray tooltip and the header of the windows name the model that types until the server has served again. With no model on this PC the dictation ends as before, and the failure says that too.
  - A provider is let go of on the thread of the message loop, so letting go never waits: the network thread of each is shut down without waiting for a request that is still under way on it (`stt/live.rs`, `Network`).
- The microphone stays warm for a while after it was used (`audio::ArmedMicrophone`, `vinput-core/src/audio/armed.rs`). Nothing is opened at start. When a session ends, its stream is stopped and emptied the moment capture ends and kept for two minutes, in which a key press only starts it again; after that it is closed, nothing is held on the device, and the next press opens the microphone from nothing as every press once did. It is not kept for good because a stream that merely exists might keep another program from taking the microphone for itself, or keep the device from saving power; neither could be measured, and what is saved is about 20 ms a press. A stopped stream captures nothing and Windows does not show the microphone as in use for it (a test in `audio/wasapi.rs` holds this on a real microphone without ever starting it; like every test there that touches a real device it runs only when asked for with `--ignored`). A kept stream is let go of when Windows reports that a device came, went or became the default, that the PC woke up, or when the microphone setting changes; nothing is kept at all unless Windows has agreed to report this, and a kept stream that was started is compared with the device a session should use, so an unreported change costs at most one session on the old microphone. If a kept stream does not start, the session opens the microphone itself. The `vinput-microphone` thread waits for the two minutes to pass while something is kept and for nothing but a message otherwise, so an idle Vinput is not woken by it. A Bluetooth microphone is never kept, because a headset may leave its music mode for as long as a capture stream exists. When a session is stopped the microphone stops at once, and what it had captured and the session had not read yet (up to the second the buffer holds) is still recognized.
- A session never waits for the provider before listening. `dictation.rs` asks for the recognizer session on the `vinput-recognizer` thread while the session thread starts the microphone (unless the provider has already said no, as without a key or a model: then the session ends with that error without listening); what is said before the session exists (the provider is still connecting right after start, after another model was chosen, after an engine update) is kept, at most a minute of it, and recognized first.
- A live microphone hands audio on in the 10 ms packets Windows delivers, without gathering them; `pipeline.rs` says why.
- With VinPUT Pro, words are typed while the server may still change them (`pipeline::run_live_session`, `vinput-core/src/inject/live.rs`). The server sends settled text and, with every message, its whole guess at what follows; typing settled text alone put a word on the screen 1.4 s after it was said at the median and 3.2 s at the 90th percentile, the guess has it there after 0.6 s. A `Typist` keeps what it typed as a guess and what should stand there now, and brings the one to the other every 10 ms, as the microphone is read: where the guess changed, it presses Backspace for the end that differs and types the new end in the same batch of key events (`TextSink::rewrite`). In the recordings in `inject/recorded/` not one character is taken back, because this server's guesses grow at their end and what it settles is what it guessed; a rewrite is the exception. What arrives is typed over about a tenth of a second, the first character at once, so the caret moves steadily and not word by word; nothing is spread out once the key is let go. Four rules keep Backspace from ever deleting anything else. Only text typed as a guess in this dictation is taken back: settled text that is on the screen as settled is forgotten. A guess is typed only as far as each of its characters is one that one Backspace deletes in any program (`erasable`: Latin, Greek, Cyrillic, Chinese, Japanese, Korean; not emoji, combining marks, the scripts written in clusters, line ends); the rest waits to be settled. Before every step the sink is asked whether the caret may be elsewhere (`TextSink::disturbed`: another window is in the foreground, or a mouse button or a key that moves the caret is down); if so, what is on the screen stands as it is and the settled text goes on after as many words, and after the second time in one dictation only settled text is typed. And nothing is typed as a guess into a program where Backspace is known not to delete the character before the caret (`NEVER_TAKEN_BACK_IN` in `inject/windows.rs`: a cell of Excel, which completes what is typed and takes the completion back first). A dictation that is called off leaves the guess where it is. Only a typed dictation does any of this: a search, and the text a program asked for, are made of settled text, and so is every dictation with another model, and with `live_typing = false` in the settings.
- A dictation that nobody speaks into ends by itself after the minutes the settings give (`audio/quiet.rs`, `UntilQuiet`): the microphone is stopped as a key stops it and let go of at once, then the sound of the stop is played, and the session says that it ended alone. Such a session types its text and does nothing else in the user's name: no Enter, no search (`dictation.rs`, `dictate`). The time is not counted while the key that started the dictation is held down, which the host tells the controller (`Controller::held`): at a start, and when a key that was only tapped comes up. Sessions a program starts are never held.
- A dictation makes two sounds, each with a switch of its own in Settings: one at the key press that starts it and one when it is stopped or called off (`vinput-core/src/sound.rs`). Both are asked for by `Dictation::start` and `stop` on the thread of the message loop, which only puts a request in a queue, so a sound waits for nothing a session does and no session waits for a sound. They are synthesized, a tenth of a second long, and die away within some 60 ms, which is what keeps the recognizer from taking them for a word when the microphone hears the speakers; the sound of the stop is asked for after the microphone was told to stop. The `vinput-sound` thread plays them on a stream to the default speakers that it keeps running, playing nothing, from the start of a dictation until two minutes after the last sound: in that time a sound is in the mix of Windows 4 to 7 ms after it was asked for. The first one after a longer rest also has to open the stream and wake the speakers, a tenth of a second where nothing else is playing. The numbers, and why nothing is held for good, are at the top of `sound/player.rs`.
- A dictation may be tidied by a language model before it is typed, and a session can edit the selection instead of typing (`vinput-core/src/rewrite.rs`). The model is the server's (`POST /v1/rewrite`) or one on this PC in `llama-server`, the engine the speech models of two files use, loaded ahead when the settings first ask for it and at every press that will need it, and let go of half an hour after it was last asked. Up to the first line break, what the model writes is typed as it arrives; the rest is pasted whole at the end, because a typed line break is the Enter key (`rewrite/shown.rs`). A selection is taken when the key goes down and replaced whole once the model is done, so a model that fails halfway leaves the user's text as it was. Whatever cannot be tidied is typed as it was said, and the session says why (`Outcome::Told`), which the host shows as a notification that leads to the Cleanup page.
- A local model lives in `whisper-server`, a child process that `vinput-core/src/stt/local.rs` starts, in a job that ends it with Vinput (`job.rs`). Its life: started (the model loads; on a graphics card one silent request follows, so the driver builds its programs then and not during the first dictation), running while in use, suspended half a minute after its last use, ended after ten minutes without a dictation, started again by the next. A suspended engine keeps the model in memory and does no work at all; left running it wakes the processor sixty to several hundred times a second. `Server::address()` is the only way to the engine: it resumes or starts it before returning, under the same lock the suspending thread takes, because a suspended process still accepts a connection and then never answers. Never connect to an engine address kept from earlier. A key press only has the engine ready (`Server::wake()`), without handing it out, so a press nothing comes of lets it be suspended half a minute later. An engine is suspended only when the record of use says it is free and Windows shows no connection of it open (if Windows cannot say, it is left running), so a request is never cut off. The Win32 side is `vinput-core/src/suspend.rs`.
- A local model with an engine server recognizes while the user speaks (`vinput-core/src/stt/local.rs` and `stt/local/`). The dictation is cut where the speaker pauses for 0.6 s (`pauses.rs`: nothing near the level of the voice, at least 2 s said), each stretch is one request on the `vinput-local-stt` thread (`stretches.rs`), and its text is typed when it comes back, in order, so the wait after the key is let go is for the last stretch alone. The engine takes one request at a time, so a stretch is cut off only while none is on its way, and only while the engine has been answering within a second and a half; a slower one (a large model on the processor) gets the dictation whole when it ends, as before. The text so far goes along as the engine's prompt. While the dictation goes on, the level of the voice decides only where a cut falls: every sample goes to one stretch or the next, and the only audio left out is dead silence (under the absolute floor in `sound.rs`) after a cut.
- The engine makes words up for audio without speech ("Thank you." for the room after the last sentence, `*phone rings*` for a click), so it is handed as little of that as can be, in four layers. `sound.rs` cuts the quiet off both ends of every stretch and sends nothing for one without sound. `pauses.rs` sends nothing for what is left after the last pause unless something in it lasts 80 ms within 26 dB of the voice, which the room and the click of the key do not; that also makes the most common ending, a pause and then the key, cost no request at all. A stretch that may not be speech (short, soft, even, far under the level the user spoke at before, or little sound after the last pause) is recognized with the language left open first, because the engine's measure of "no speech" is next to zero whenever it is told the language, and only what passes is taken or asked for again in the language of the dictation (`dictation.rs`, `Care`); such a stretch goes without the prompt and is not typed if the engine was unsure of it or it only repeats itself or the end of the text. Last, `phantoms.rs` takes the names of sounds out of every answer, and drops the phrases the engine is known for making up, but only from a stretch in which nothing was as loud as the voice. The recordings in `stt/local/clips` and the tests beside them hold this, one of them against the engine itself (`--ignored`). A model whose program runs once per dictation (`Runner::Command`) is recognized whole as well.
- A model that comes as two files (Qwen3-ASR; `Runner::Listener` in `models.rs`) runs in a second engine, `llama-server` of llama.cpp, with the same life as the first. It is a language model that is shown the recording and writes down what it hears, so it is asked in another form (`converse` in `stt/local.rs`): the recording goes in a chat request, the answer is started with the language when that is known, and what comes back is put in the form of the first engine's answer. Such a model cannot be led as Whisper can (`Inference::led`). It does not carry on from the text so far, and writes every stretch as a sentence of its own, with a capital and a full stop (started with the text so far it drops what follows a finished sentence), so its dictations are not cut at pauses: each is one stretch, recognized when it ends. And told a language it finds words in a click and writes them as if they were speech, so a stretch that may not be speech is typed only if the model hears a language of the user's in it on its own. A dictation that goes on for minutes is cut all the same, at the first pause after two minutes, so that no request is longer than the engine answers in time; how long a request may take grows with its recording, up to nine minutes. The engine has one build, for Vulkan, started with `--device none` for the processor and `--device Vulkan<n>` for the card; left to itself it spreads a model over every card of the PC. Which card: an engine left to choose takes the first one Windows hands it, which on a PC with graphics in its processor and a card beside them is often the wrong one. So each engine program is asked once which cards it sees and told the number of the one Settings name, the card with the most memory of its own (`vinput-core/src/stt/local/cards.rs`; the first engine and the programs that run once a dictation get `-dev <n>`). An engine that cannot use the card it was told does not fail, it runs the model on the processor; so what the first engine says of the card as it loads a model is listened for, and an engine that lists no card at all is noted, and while either holds the windows say the model runs on the processor (`stt::fell_back`, `Facts::card_use` in `vinput-host/src/view.rs`). Nothing an engine prints is kept. It is started without the `LLAMA_` variables of the user's environment and with a key made up for that start (`LLAMA_API_KEY`), which every request of Vinput carries, so that no other program and no page in a browser can use it. Which languages a model knows is `Model::languages`; Settings say so on the row of a model that lacks a configured one, and nothing keeps anyone from dictating with it.
- The engine is never asked for language likelihoods on the way (`stt/local/dictation.rs`); that is a second pass over the audio on every request. One configured language is named to it. With several it detects the language and names it in its answer; only if that is not a configured one is the stretch recognized again in a configured one, that once with the likelihoods to choose by. Every stretch is detected afresh until two in a row agree or one language has been heard for eight seconds on end; from there it holds for the rest of the dictation.
- An action of the user's own is a key that hands what was said to a program they named (`vinput-core/src/actions.rs`). Vinput carries no scripting language: a script is a program like any other, so what it can be made to do grows without the executable growing. Its session is a dictation like a search, `Target::Action`, tidied first if the action asks for it, and its text goes to the host as `Outcome::Action`. The host starts the program on `vinput-action`, with the text on its standard input, in `VINPUT_TEXT`, and in place of `{text}` where that is an argument of its own; the arguments are split once, as Windows splits a command line, and no shell ever reads the text. The program runs without a console window in the user's folder and is ended after the time the action allows; the thread waits for its end through Windows (`job::Exit`), so nothing is looked at again and again. What it wrote is typed or put on the clipboard on that thread, and a failure comes back to the loop as `ACTION_DONE` and is said in a notification. Each action has a hotkey id of its own from 20 on (`hotkeys.rs`), and its rows on the Shortcuts page are named by its place on the list, so there are at most eight.
- What a recognizer writes is put into the user's own words before anything is typed, guessed or handed on (`vinput-core/src/words.rs`, `words/shape.rs`). The settings hold a dictionary (a word, and optionally what it sounds like), snippets (a phrase and the text typed for it) and a switch for spoken formatting (`new line`, `new paragraph`, `snake case`, `camel case`, `kebab case`, `all caps`). `dictation.rs` wraps the provider of every session (`InOwnWords`), so each session is a `Shaped` recognizer whatever the provider and whatever becomes of the text; without a dictionary, snippets or the switch nothing is wrapped. Text arrives in pieces that end anywhere, so a `Shaper` passes on what nothing can change any more and keeps the start of what may still become a phrase; what it has passed on in the end is what the whole text shaped at once would be, which a test holds for every way of cutting a text. Where words are typed while they may still change, what is kept is shown as part of the guess, so nothing is on the screen later than before. A command counts only where it was said as one, which the recognizer's punctuation shows: at the start or after a mark, and for a line break with a mark or the end after it; the rules and their reasons are at the top of `shape.rs`. The commands are English in every language. The dictionary is also what a recognizer is asked to listen for (`words::listened_for`, one list for the process, read when a session starts): the first engine reads it ahead of the text so far in its prompt, the second in a message of the system (the field `context`), and VinPUT Pro is sent it as `terms` in the first message of a stream, which its server hands to a speech service that takes such a list. Google Cloud and Gemini with a key of one's own are not handed it; the spelling afterwards works with them all the same.
- Downloads, the model lookup, the update check, the Google token request and the questions the setup of a Google service asks Google (`vinput-core/src/stt/check.rs`) are plain HTTPS requests through WinHTTP (`vinput-core/src/net.rs`), made on the thread that needs them. Nothing of them is held while idle. So are the requests about the VinPUT Pro account (`vinput-core/src/cloud.rs`). Its server is the one address in that file: a build that ships talks to no other, whatever its environment says, and opens in the browser only a page of that server for signing in and a page of the payment service for paying. Only the speech streams (gRPC to Google Cloud, a WebSocket to Gemini, one to VinPUT Pro) use the TLS library in the executable.

## The programs beside Vinput

Vinput is one program of a family. The others live under `apps/`, are built from the same shared code and window toolkit, have versions and releases of their own, and are small for the same reasons Vinput is.

- **Which program a process is** it says once, first thing in `main` (`putlab_core::product::set`): the name of its folders under `%APPDATA%` and `%LOCALAPPDATA%`, its log, what its requests say they are from, its version, where its releases are published and what its setup program is called. A process that says nothing is Vinput, by the names it always had. The sign-in is the exception to "each its own": every program reads the same entry of the credential store (`Vinput/vinput-pro-session`), so signing in to one signs in all of them.
- **Whose pages an executable carries** is a feature of `vinput-view` and `vinput-ui`: `vinput` (the default), `hub`, `voutput`. Each program asks for its own, the ones under `apps/` with the default turned off, so the hub has none of Vinput's pages in it and Vinput none of the hub's. `Page::app()` says which program a page belongs to; the navigation pane, the name at its head and the foot under it follow from that (`vinput-ui/src/pages.rs`, `shell.rs`). When the whole workspace is built at once (`cargo lint`, `cargo test --workspace`) cargo turns every feature on, so Vinput's code sees the pages of the others; the three places in `vinput-host` that list pages or commands have an arm for "not one of mine", which a build of Vinput alone never reaches. Two more features of `vinput-ui` follow from those: `line`, the line to the background process that started a window, and `pickers`, the parts of a page that pick from a long list. Vinput and Voutput have both. The hub is its own backend and has no such page, so it has neither, and is some 150 kB smaller for it.
- **A separate copy** works for every program as it does for Vinput, with the same `VINPUT_INSTANCE`: `%APPDATA%\Voutput-test`, `%APPDATA%\PUTLAB-test`. What "keeps to itself" means is each program's own, below.

### The hub

```text
putlab.exe                 exists only while its window is open; nothing is resident
  main thread        the window (vinput-ui), with the hub itself as its backend
  putlab-hub         owns everything the hub knows (state.rs); one message at a time
  putlab-job         one per request, download, setup program or question to the account
  putlab-look        every three seconds while the window is open: what is installed?
```

- `apps/hub/src/state.rs` is the whole rule book: a command of the window or a report of a thread goes in, jobs come out, and it touches nothing else, so it runs in tests without a server or a setup program. `system.rs` carries a job out; `backend.rs` is the thread between the two and the window. The window has no background process to talk to, so it is handed the backend directly (`vinput_ui::Source::Program`).
- The programs it knows are a small file on the site, `products.json` beside the release manifests (`catalog.rs` has its form and what is refused in it), or the list built in until the site has one. Which are installed it reads off their folders under `%LOCALAPPDATA%\Programs` and their entries under "Installed apps" (`installs.rs`); a Vinput installed without the hub is found the same way.
- Installing is the program's own setup: the hub downloads it, checks it against that program's `latest.json` (`putlab_core::update`), and runs it with `--install --quiet` or `--update`, the switches under "What must stay compatible". It writes nothing of its own about what is installed.
- A separate copy of the hub changes nothing on the PC it runs on: it downloads and checks a setup program and does not run it, starts and removes no program, and opens nothing in the browser (`system.rs`).

### Voutput

```text
voutput.exe --background           resident, one per user
  main thread        message loop: the two keys, Escape while reading, the tray icon
  voutput-reading    one per reading: selection -> [model] -> sentences -> voice -> speakers
  voutput-install    one per download of a voice, a model or an engine
  voutput-window     reads what the Settings window says
  voutput.exe voice-engine  child process, only with a voice of the voice engine: keeps the model loaded; ended ten minutes after its last sentence
  voutput-engine     one per start of the model engine: loads the model and makes the graphics card ready
  llama-server       child process, only with a model on this PC; kept for as long as Voutput runs
  voutput-served     one per sentence of a large voice, and one per start of its server
  zonos2-server, audiocpp_server  child process, only with Zonos2 or Higgs TTS 3 as the voice; kept as the model is

voutput.exe ui <window>            exists only while the Settings window is open
```

- A reading is `text -> [Summariser] -> sentences -> Voice -> Output` (`apps/voutput/src/reader.rs`); each stage is a trait with a fake for tests and runs on a thread of its own, so the first sentence is spoken as soon as it is made, the voice works at most two sentences ahead of the speakers, and a summary is spoken while the model is still writing it. One flag stops all of it.
- The selection is asked for through UI Automation, which touches nothing; only where a program does not answer is Ctrl+C sent and the clipboard read. Everything on the clipboard is kept first, in every form it is there in (formatted text, a picture, a list of files), and put back afterwards; where something on it cannot be kept whole, nothing is copied at all. Ctrl+C is pressed only once the keys of the hotkey are let go of (`selection.rs`).
- The voice and the model that sums up are chosen apart from each other (`catalog.rs`, `app.rs`). What runs on this PC is a download and an engine, pinned by address, size and SHA-256 like Vinput's: sherpa-onnx for the voices, and the same llama.cpp release Vinput pins for the models. The engine of a model is started without the user's `LLAMA_` variables and with a key made up for that start, as Vinput's is (`putlab-core/src/engine.rs`). How a model would run on this PC is `catalog::model_fit`, drawn from `putlab_core::hardware`.
- A model on this PC is made ready before anyone asks for a summary (`putlab-core/src/engine.rs`, `App::warm`): when Voutput starts, when the model is picked, and when the graphics card is switched. Ready means loaded and, on a graphics card, asked for one summary of a made-up text of some 400 words. The driver of a card builds the programs the card runs when they are first used and keeps them on disk; measured with an empty cache that first summary took 30 s on an idle PC and 107 s on a busy one, against 0.2 s for every one after it, and a text of a dozen words did not build what a long one needs. That wait is what the first try of Voutput ran into at the first press of the key, with nothing on screen. Now the row of the model says where it stands (`Pick::status`), a key pressed meanwhile waits and says so, and what the engine writes goes to `engine.log` beside the settings. The engine runs on the graphics card whenever there is one the user has not switched off, on the card Windows calls the best, which the engine does not always list first (`device_for`); if the card cannot run the model the processor does, and the row says so. The CUDA build of the engine was measured against the Vulkan one on the same card: the same time to the first word and the same pace once both were ready, a first summary of its own of 22 s, and a download twenty times as large. So there is one build, for cards of any make.
- The model stays loaded for as long as Voutput runs, so that no summary waits for a load; `free_graphics_memory` in the settings ("Free graphics memory when idle") lets it go half an hour after its last summary instead. An engine that ends by itself, as when a driver is replaced under it, is started again at once by the thread that made it ready, which waits on the end of the process and looks at nothing meanwhile (`Engine::keep`, `job::Exit`); three such endings within a minute of being ready each are taken for a fault and said in the row. While the model is being made ready its row shows a bar (`Pick::busy`): how far the load is, going by the memory the engine holds against the size of the model's file, which is the only sign of it there is; and a bar that only moves, with the seconds so far, while the driver builds the programs of the card, which gives no sign at all. That second step is named only once it has lasted two seconds, which it does only the first time on a PC, and the tray icon then says so once.
- A voice of the voice engine stays loaded between sentences (`kept.rs`). Starting the engine's program for each sentence cost 1.5 to 1.9 s every time, nearly all of it loading the model again. So the model is loaded once, in a helper: this same executable started as `voutput voice-engine <library> <model>`, which loads the engine's library (`sherpa.rs`, the C interface of the pinned release, field for field), and speaks each sentence it is sent as a line of JSON on its standard input, answering with the samples on its standard output. Voutput itself stays as small as it was, and a fault in the engine ends the helper and not Voutput. Measured with the model loaded, on a desktop processor: Piper has the first piece ready after 0.07 s, Supertonic after 0.4 to 0.5 s. The first reading after ten idle minutes also loads the model, about a second. Each sentence reaches the helper over a pipe: what the user selected is never on a command line, where every program on the PC could read it.
- Supertonic makes a sentence in steps, five by default, and its time is those steps: three would bring the first piece to 0.3 s and two to 0.2 s, but both clip (the loudest sample reaches full scale, which five steps never come near), so the usual number stays. `VOUTPUT_VOICE_STEPS` sets it in a build for development, for making clips to compare by ear.
- Two large voices need a graphics card and are speech servers of their makers' (`served.rs`): Zonos2 by `zonos2-server` of Zyphra, Higgs TTS 3 by `audiocpp_server` of audio.cpp. Voutput starts the server when that voice is chosen and when Voutput starts, asks it for each sentence on a port of this PC, and keeps it as it keeps a model that sums up: for as long as Voutput runs, or for half an hour after its last sentence where the user has the memory of the card freed. Neither server takes a key; they listen on this PC only and all they can be asked for is speech. Measured on a desktop graphics card with the model loaded: Higgs has the first piece ready after 0.7 s and makes 15 s of speech in 4 s; Zonos2 has it ready after 1 to 3 s and makes 14 s in 9 s. Loading takes Higgs about 10 s and Zonos2 about 5 s, and longer the first time, while the driver of the card builds what the card runs. On a processor both are slower than speech, so they are not offered a start without a card.
- Zonos2 does not always stop at the end of a sentence: in the trials about one try in four ran on with more sound, whatever the settings. So each sentence is given as many frames as its length can need (`served::bounds`), and one that used them all, or came out far too short, is asked for again with other random numbers, three times at most. It is offered for English, the language it was tried in.
- Higgs copies the voice of a clip it is handed, and without one speaks with a voice of its own that drifts a little between sentences. The first sentence it speaks in a language is kept and handed to it with every later one, so the voice stays the same and no recording of anyone is shipped or downloaded. When its server starts it speaks two short sentences nobody hears, which is when the card is made ready. The file of Higgs that audio.cpp reads is published by the makers of audio.cpp, not by Boson; it is the same model under Boson's licence, which allows research and personal use only, and its row says so.
- The first sentence of a reading opens with a short piece (`text::opening`): the wait for the first sound is the time the voice takes for the first piece, so a long first sentence is cut after its first comma, where a speaker would pause anyway, or after the last whole word within sixty characters where it has none.
- Which language a text is in, Windows says (`language.rs`), so a voice that speaks several is told and nothing has to be set.
- A copy that keeps to itself plays nothing and presses no key in anyone's program: its output is thrown away and the selection is only ever asked for, never copied (`host.rs`). The one-shot commands (`voutput say <text> --wav <file>`, `voutput summarise <file>`) write what would be heard to a sound file, which is how a voice is tried out without the speakers.
- Never start a build of `voutput.exe` by itself with no arguments or with `--background` on a PC whose user is at work: it takes the two keys from every other program. The one-shot commands and `ui ... --mock` are safe.

## The resident process, module by module

`crates/vinput-host/src/windows.rs` holds `Host`, which owns every Win32 resource and every piece of state, and the numbers of the messages other threads wake it with. Each module under `windows/` adds the part of `Host` it is about; only the thread that runs the loop touches it.

| Module | What it does |
| --- | --- |
| `windows/run.rs` | The message loop and the procedure of the hidden window; replays what arrived while the tray menu was open (every message another thread wakes the loop with is in `WAKES`) |
| `windows/instance.rs` | One Vinput at a time: the mutex, finding the running copy, asking it to show Settings or to exit |
| `windows/hotkeys.rs` | Registering the hotkeys, asking whether a key is free, letting go of them while Settings captures one |
| `windows/sessions.rs` | Starting, watching and ending sessions; the indicator, the `state` file, what a session leaves behind. The first frame of the indicator is drawn as the session starts; that a session has ended arrives as `SESSION_ENDED`, and `Ending` says what it comes to |
| `windows/apiserve.rs` | Carrying out commands of the local API; `decide` is the whole rule book |
| `windows/tray.rs`, `traymenu.rs` | The icon, tooltip and notifications; the menu and what a pick does |
| `windows/children.rs` | The window processes: started, told nothing before they are up, shown pictures, let go of |
| `windows/picture.rs` | Gathering the facts a `View` is drawn from (`view.rs` draws it). What is read off the model and engine folders is kept from one tick of the window timer to the next, and read again after anything the host did or heard, during an install, and every two seconds |
| `windows/commands.rs` | Every `Command` of a window, carried out |
| `windows/picker.rs` | The file and folder pickers, each on a thread of its own |
| `windows/updates.rs` | Update check, download and hand-over to setup |
| `windows/pro.rs` | VinPUT Pro: every request to its server on a thread of its own, which wakes the loop with `PRO_HEARD`; the wait for a payment made in the browser, which a busy server does not end and which always says when it is over |
| `windows/google.rs` | The setup of a Google service of one's own: its steps, what was entered and not kept yet, and each question to Google, and the reading of a key file, on a thread of its own, which leaves its answer in a queue and wakes the loop with `GOOGLE_CHECKED`. An answer nobody waits for any more (a newer question, the page left, the window closed) is dropped. Nothing is kept or put to use before the user finishes the setup |
| `indicator.rs`, `draw.rs` | The listening indicator: a layered window, its phases and where it goes, put back above every other window each time it is shown; the picture in it |

| `win.rs` | Small Win32 helpers, and what may be handed to the shell to open |

## A second copy beside the installed one

For trying a build out on a PC where Vinput is installed and running, set the environment variable `VINPUT_INSTANCE` to a short name (ASCII letters, digits and dashes, at most 32). Every name by which a running Vinput is known then ends in `-<name>`: the single-instance mutex, the class and title of the hidden window, the API pipe (`\\.\pipe\vinput-<name>`), the credential-store entry, and the folders `%APPDATA%\Vinput-<name>` and `%LOCALAPPDATA%\Vinput-<name>` (settings, `state`, log, models). Such a copy neither finds nor disturbs the installed one, and it never writes what belongs to the install: no startup entry, no Start menu entry, no setup, update or uninstall. The naming is `vinput-core/src/instance.rs`. Without the variable every name is what it has always been.

```powershell
$env:VINPUT_INSTANCE = "test"; cargo run -p vinput -- --background
```

Its hotkeys start out the same as the installed copy's, which holds them; set others in `%APPDATA%\Vinput-test\settings.ini` first, or in its Settings. Stop it with Quit in its tray menu.

A separate copy keeps to itself on the desktop as well (`instance::is_quiet`, the one place this is decided): it shows no tray notification and no error box and plays no sound, those of a dictation included. What it would have said goes to its log, `%APPDATA%\Vinput-<name>\vinput.log`. It is there to be tried out and driven by scripts, beside a Vinput whose user must not be told of failures that are not theirs. Its tray icon, its indicator and its windows are as they always are.

Whatever cargo runs from the repository is such a copy without being told. `.cargo/config.toml` sets `VINPUT_INSTANCE` to `dev` for every process cargo starts (`cargo run`, `cargo ui`) unless the variable is set already, so the one-shot commands of the README read and write `%APPDATA%\Vinput-dev` and `%LOCALAPPDATA%\Vinput-dev`, with settings and models of their own. To run one of them over the settings and models of the installed Vinput, set the variable to something that is not a name, such as a dot, and run it through cargo as always: `$env:VINPUT_INSTANCE = "."; cargo run -- models`. Do not start `target\debug\vinput.exe` by hand for that: cargo builds the same file for more than one purpose, and after a `cargo test` it may be the build for tests, which is the copy `tests` whatever it is told (below). `cargo run` always builds the one meant to be run first. Only cargo reads `.cargo/config.toml`: the executable that ships is the same with or without it, and started by itself, as an installed one is, it is the one and only copy.

Tests do not depend on that file. `vinput-core` built for its own tests, or with its feature `test-instance`, which every other crate asks for among its dev-dependencies and nothing asks for among its dependencies, runs as the copy `tests` when the variable names none, or names only the `dev` that cargo gives everything: tests have folders of their own (`%APPDATA%\Vinput-tests`), apart from those of the copy a developer runs, and a name set by hand is still taken. A test binary started in any way therefore never writes to the log, the settings or the `state` file of the installed Vinput, and can show or play nothing. A crate that gains tests and depends on `vinput-core` gets the same dev-dependency.

## What must stay compatible

Installed copies update themselves and other programs talk to them, so these are contracts with the past:

- **`%APPDATA%\Vinput\settings.ini`.** A newer version reads an older file as it is, fills in defaults for keys it adds, and writes back keys it does not know. Never rename a key or give one a new meaning; add a new key. `settings.rs` has a test for this; keep it passing.
- **`%APPDATA%\Vinput\state`.** Holds the word `listening` or `idle` for tools that poll. Keep the path and the two words. Failing to write it must never affect dictation.
- **The local API** (`\\.\pipe\vinput`, `docs/api.md`). Additions only: new events, fields, modes, commands and error codes, which both sides must ignore when unknown. `protocol` stays `1` unless an existing client would break.
- **The update manifest** (`latest.json`: `version`, `notes`, `url`, `sha256`, `bytes`, `published`) and the setup program's name, `VinputSetup-<version>.exe`, which is what makes the executable install instead of run. Released versions read both. From the first signed release on a manifest also carries `signature`, the publisher's, without which no later version takes the release; what is signed (`update::signed_text`) and the key that checks it (`update::PUBLISHER`) are contracts as well, and so is the site's address (`update::SITE`), the only place a setup program is fetched from. See "How an update is trusted" in `docs/release.md`.
- **How an update hands over.** A released version starts the setup program it downloaded with `--update` and exits. The setup program is the new version, so what happens next is its own business: it replaces the program and starts it with `--updated`, which shows the About page and a notification, so the user sees that Vinput is back. Keep `--update` meaning "install without asking, then start the new version so that it shows itself"; `--install --quiet` is for tools and starts it in the tray.
- **Folders.** Settings, log and the model list in `%APPDATA%\Vinput`; models and the engine in `%LOCALAPPDATA%\Vinput`; the program in `%LOCALAPPDATA%\Programs\Vinput`; keys in the Windows credential store, under the names in `vinput-core/src/secrets.rs`, which stay as they are. An update replaces the program folder and nothing else.

The line between the resident process and a window process is not such a contract: both ends are the same executable, so `vinput-view` may change freely as long as both sides change together. Keep its enums in serde's plain form, and lists of plain choices as numbers (`sent_as_number!`): `tag` and `content` are read through a buffer, which costs the executable a second copy of everything under them.

- `cargo lint` is clippy for the whole workspace with warnings as errors, as CI runs it. CI then lints each program by itself as well (`cargo clippy -p vinput --all-targets --locked -- -D warnings`, and the same for `putlab-hub` and `voutput`), because built alone a program has only its own features, which is how it ships. The lints are in the root `Cargo.toml`: clippy `pedantic`, no `unwrap`, `expect` or `panic`, public items documented, `unsafe_code` denied except in modules that call Win32 and say so with `#![allow(unsafe_code)]` and a `SAFETY` comment on each block.
- `cargo size` builds the shipping executable into `target\size\release\vinput.exe`. CI fails when it passes the budget in `.github/workflows/ci.yml`; see "How big a release may be" in `docs/release.md`.
- Do not set a `RUSTFLAGS` environment variable for a build that ships: it replaces the flags in `.cargo/config.toml` that link the C runtime in.
- Never start a build of `vinput.exe` by itself with no arguments, or with `--background`, `--install`, `--update` or `--uninstall`, on a PC where Vinput is installed and running, unless `VINPUT_INSTANCE` is set (see above): it talks to, replaces or removes the installed copy. Through `cargo run` it is the copy `dev`, which does none of that. One-shot commands (`models`, `check-update`, `transcribe`, `encode`, `ui ... --mock`) are safe. Build into a `--target-dir` of your own when several checkouts build at once.
- Toolchain pinned in `rust-toolchain.toml`. Windows only: the engine compiles elsewhere, but capture, typing and the host do not exist there.
